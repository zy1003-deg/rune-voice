# Rune Voice — Project architecture

> Audience: code reviewers, prospective contributors, and the future
> maintainer who inherits this repo.

This document describes what each piece of the project does, how data flows
between them, and where to start reading. It is intentionally honest about
what is *not* present (e.g. there is no application server — the "backend"
is really an offline data pipeline; and the production dataset is hosted
externally, not in this repository).

---

## 1. Overall architecture

Rune Voice is composed of two **independent** halves:

1. **Offline pipeline (Python)** — pulls operator-supplied source-of-truth
   metadata + audio, decodes WEM → MP3, and emits static JSON files.
   Never runs at request time.
2. **Runtime (browser SPA)** — reads JSON from the operator's
   `VITE_API_BASE` (default: bundled synthetic demo dataset), plays audio
   from the same base, and serves a static HTML/JS bundle from Vercel
   (or any static host).

### Repository vs Production data

The **repository** ships:
- Source code (Python pipeline + React/Vite frontend).
- Schemas, tests, documentation.
- A small **synthetic demo dataset** under `web/public/demo-data/` —
  5 fictional entities, ~20 synthetic quote records, no audio.

The **production dataset** lives outside the repository. It is the
operator's responsibility, hosted wherever `VITE_API_BASE` points at
runtime (typically object storage + a small JSON hosting layer). The
production data path is intentionally **not** included in this repo's
`git` history.

### Offline data pipeline (operator-side)

When an operator wants to refresh their dataset, they run the pipeline
against a source they have permission to use:

```
  Operator-supplied voice metadata host
                │
                ▼
  core/crawler.py (asyncio + httpx)
                │
                ▼
  store/audio_store.py (writes .wem, runs vgmstream + ffmpeg)
                │
                ▼
  Local audio tree (./data/audio/<entity>/<skin>/<quote>.mp3)
                │
                ▼
  web/generate_data.py, add_roles.py, update_events.py,
  generate_search_index.py, generate_sitemap.py
                │
                ▼
  Static JSON dataset
                │
                ▼
  Uploaded to operator's CDN / bucket
```

None of the pipeline output is committed to this repository.

## 2. Frontend architecture (`web/src/`)

### Component tree

```
main.jsx
  └─ App.jsx                       (global state + hash router)
       ├─ Navbar.jsx               (search input, theme toggle, logo)
       ├─ HeroSection.jsx          (landing hero, "surprise me" button)
       ├─ RoleTabs.jsx             (pill filter)
       ├─ ChampionCard.jsx         (grid card, memoized)
       ├─ ChampionDetail.jsx       (per-champion view: skins, events, quotes)
       └─ PlayerBar.jsx            (fixed bottom global player)

Custom hooks:
  ├─ useAudioPlayer.js            (singleton <audio> + playlist state)
  ├─ useDebouncedValue.js         (generic debounce)
  └─ useTheme.js                  (light/dark, localStorage-persisted)

Utilities:
  ├─ utils/audioUrl.js             (buildAudioUrl, buildAvatarUrl)
  └─ utils/search.js               (loadSearchIndex, searchQuotes, ...)
```

### State management

Pure React (`useState` + `useMemo` + `useCallback`). No Redux / Zustand.
Routing is hand-rolled: `App.jsx:35-41` reads `window.location.hash` on
mount, and the `popstate` listener (`App.jsx:47-68`) keeps state and URL in
sync. Champion deep-links use `#/champion/<urlencoded name>`.

### Global keyboard shortcuts (`App.jsx:86-112`)

- `Space` — toggle play / pause (ignored while typing in inputs)
- `←` / `→` — previous / next track
- `Esc` — stop and close the player

### Singleton audio engine (`hooks/useAudioPlayer.js`)

A module-level `<audio>` element is created once and shared by every
component. `play(id, url, info)` toggles pause if the same id is requested
again; otherwise it stops the current track, instantiates a new `Audio(url)`,
applies volume, and prefetches the next track via `<link rel="prefetch">`.
Progress is updated with `requestAnimationFrame`.

## 3. "Backend" architecture

> **There is no application server.** Calling this project "full-stack"
> would be misleading.

What *is* present:

- **Crawler** (`core/`, `store/`, `utils/`, `config.py`, `main.py`) — an
  asyncio + httpx + aiofiles pipeline that runs **once** to refresh the
  offline audio tree.
- **Data-prep scripts** (`web/generate_*.py`, `web/add_roles.py`,
  `web/update_events.py`, `web/role_utils.py`)
  — also one-shot, run after the crawler.
- **Local static dev server** (`web/serve.py`) — a stdlib
  `http.server.ThreadingHTTPServer` that serves `/data/*.json` from
  `web/public/data/` and audio from `LOL_VOICE_SERVE_AUDIO_ROOT`
  (default `./data/audio`) for local development.

## 4. Data structures

### Demo dataset (`web/public/demo-data/data/`)

The repository ships a **synthetic** dataset under
`web/public/demo-data/data/`. This is what `npm run dev` loads by default
and is what fresh clones use to demonstrate the UI.

#### `web/public/demo-data/data/champions.json`

Top-level: array. 5 fictional entities.

```json
[
  {
    "name": "Alpha Warrior",
    "alias": "alpha",
    "quoteCount": 5,
    "skins": ["Default"],
    "file": "alpha.json",
    "role": "fighter"
  }
]
```

#### `web/public/demo-data/data/quotes/<entity>.json`

Top-level: array, 3–5 records per fictional entity.

```json
[
  {
    "skin": "Default",
    "event": "Select",
    "text": "Demo select line 1 — the warrior steps forward.",
    "file": "demo_alpha_select_1.mp3",
    "dir": "alpha/Default"
  }
]
```

Note: the audio files referenced in the demo dataset **do not ship**.
The player gracefully reports "audio unavailable" — the search, navigation,
and player UI all still work.

#### `web/public/demo-data/data/search_index.json`

Top-level: array of 20 entries. Used by `web/src/utils/search.js`.

#### `web/public/demo-data/data/featured_quotes.json`

Top-level: array of 3 entries. Powers the "Surprise me" landing action.

### Production dataset (operator-side, outside this repo)

When an operator deploys this platform, they generate their own dataset
using the pipeline in `core/` + `web/generate_*.py`. The production
schema is identical to the demo schema. Records can number in the tens of
thousands; audio files are MP3 hosted alongside the JSON.

The production JSON files live wherever `VITE_API_BASE` points. They are
**not** tracked in this repository.

## 5. API

> None at runtime.

The only HTTP surfaces in this project are:

| Where                          | Method | Path pattern     | Purpose                                  |
| ------------------------------ | ------ | ---------------- | ---------------------------------------- |
| `web/serve.py` (dev only)      | GET    | `/data/*`        | JSON metadata read by the SPA            |
| `web/serve.py` (dev only)      | GET    | `/<file-or-dir>` | Audio files served from disk             |
| Vercel (prod)                  | GET    | `/<asset>`       | Vite-built static assets                 |
| `VITE_API_BASE` (prod)         | GET    | `/<dir>/<file>`  | Audio streamed from object storage       |
| Third-party (crawler only)     | GET    | `/lol-*/v1/...`  | Source of truth, not part of our project |

There is **no JSON-over-HTTP API** serving the frontend. The frontend
reads JSON via static HTTP (`fetch('/data/champions.json')`).

## 6. Audio file processing

Game voice files are delivered as `.wem` (Wwise encoded audio). The
pipeline:

1. `core/client.py::download_audio` → fetches raw bytes.
2. `store/audio_store.py::save_audio` → writes bytes to disk with the
   intended `.mp3` filename.
3. `utils/help.py::convert_wem_to_mp3` →
   - Calls `vgmstream-cli -o <out>.wav <in>.wem` to decode WEM → WAV.
   - Calls `ffmpeg -y -i <in>.wav -codec:a libmp3lame -qscale:a 2 <out>.mp3`
     to encode WAV → MP3.
   - If `ffmpeg` is missing, leaves a `.wav` next to the `.wem`.
   - If `vgmstream-cli` is missing, warns and leaves the `.wem` on disk.

External dependencies (not bundled):

- `vgmstream-cli` — install from
  <https://github.com/vgmstream/vgmstream/releases>.
- `ffmpeg` — system package manager.

## 7. Data processing pipeline

End-to-end:

```
1. (operator-side, outside repo)
   python main.py --mode full
   └─ core/crawler.py iterates entities
      └─ core/client.py fetches metadata + audio
         └─ store/audio_store.py writes .wem + invokes WEM→MP3

2. (operator-side, outside repo)
   python web/generate_data.py
   └─ scans ./data/audio/<entity>/<skin>/<quote>.mp3
   └─ writes <output-dir>/quotes/<entity>.json
   └─ writes <output-dir>/champions.json

3. python web/add_roles.py            # backfills role field

4. python web/update_events.py        # refreshes event metadata

5. python web/download_avatars.py    # removed from public release     # (removed from public release)

6. python web/generate_search_index.py
   └─ aggregates all quotes/*.json into a single search_index.json

7. python web/generate_sitemap.py
   └─ emits sitemap.xml from champions.json

8. Upload the resulting JSON + audio to the operator's CDN / bucket
   and point VITE_API_BASE at it.
```

Each step is idempotent. The pipeline can be re-run after the operator's
source data changes. The output of step 2 is written to a directory of the
operator's choosing (default `./data/output/`, configurable via the scripts).
It is not written into `web/public/data/`, which is gitignored.

## 9. Deployment

### Repository-side (this codebase)

- Fresh `git clone` → `cd web && npm install && npm run dev` boots the SPA
  with the bundled synthetic demo dataset (`web/public/demo-data/`).
- The SPA loads `/demo-data/data/champions.json` etc. by default.

### Production (operator-side)

- **Static SPA**: `cd web && npm run build` → `web/dist/`, deployed to any
  static host (Vercel, Netlify, Cloudflare Pages, S3+CloudFront, …).
- **Dataset + audio**: hosted on object storage (S3, R2, COS, OSS, MinIO, …).
- **Configuration**: `web/.env.production` sets `VITE_API_BASE` to the
  dataset's public URL.

### Self-hosted alternative

Any combination of:

- Static host for the SPA.
- S3-compatible bucket for the dataset + audio.
- GitHub Actions for CI (configured under `.github/workflows/`).

### Local dev

```
cd web && npm run dev   # Vite dev server on :5173 (uses /demo-data)
```

`web/serve.py` remains as an optional local-data server for operators
who want to test their pipeline output without uploading it.

The maintainer historically hosted an instance of this project for a
League of Legends fan content dataset on a personal domain; that host
is not part of this repository and is documented here only as an
example. New deployments should pick their own host and configure
`VITE_SITE_URL` accordingly.

The production deployment in use at <https://lol.zyyeah.asia> historically
pointed at Tencent Cloud COS; that bucket URL is the operator's local
`web/.env.production`, which is gitignored.

## 13. Known limitations / future work

- **Search is in-browser substring match.** Fine for tens of thousands
  of entries but will need to move to a server or pre-built inverted
  index if the archive grows by an order of magnitude.
- **No TypeScript.** Acceptable for the current size but will hurt as
  the schema evolves.
- **Accessibility** (A11y) of the player controls and entity cards is
  partial; the `ChampionCard` and quote rows are clickable `<div>`s.
